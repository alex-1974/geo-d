# geo-d v2 public API audit

## Status

Completed public-API migration audit for the `v2.0.0` integration defined by
ADR-0019 and ADR-0020.

This document records the complete frozen `geo-d` v1 public surface, the
declaration-by-declaration v1-to-v2 disposition, and the reproducible
implemented v2 public surface.

Completion of this audit does not by itself declare the v2 API frozen and
does not add new geometry functionality.

The family-decision sections intentionally preserve parts of the chronological
review process. Earlier wording such as candidate, review, or future probe is
superseded where a later family-result section, package-coexistence result, or
the implemented v2 audit result below records the final decision.

## v2 objective

`geo-d` remains a coordinate-system-agnostic Euclidean 2D library.

The v2 migration exists to make the established 2D API form a predictable
family with the independent `geo3-d` sibling library.

This requires consistency in:

- dimensional type naming;
- operation-family naming;
- overload structure;
- argument ordering;
- UFCS receiver choice;
- parameter naming;
- result-type naming;
- compatibility/deprecation;
- simultaneous `geo` / `geo3` use.

No `geo3-d` implementation is required for the v2 freeze.

A design-level or compile-only 3D model is sufficient.

## D language constraints relevant to the migration

### UFCS

For a free function, D UFCS uses the first function parameter as the object
expression.

Therefore:

~~~d
operation(receiver, other);
receiver.operation(other);
~~~

are two call forms of the same API design.

The first parameter is consequently part of the intentional API ergonomics.

### Named arguments

D resolves named arguments against parameter names.

Public parameter names and their ordering must therefore be reviewed as part
of source compatibility rather than treated only as implementation detail.

### Deprecation

D supports deprecated declarations with migration messages.

Where semantics and overload resolution permit it, v1 names should remain as
deprecated aliases and v1 signatures as deprecated forwarding overloads
through the v2 line.

Compatibility declarations must not maintain independent implementations.

### Independent imported overload sets

Functions with the same name in different imported modules remain distinct
overload sets.

With both modules imported, an unqualified call is valid when exactly one
overload set matches. A call is ambiguous when matching candidates are found
in more than one imported overload set.

Consequences for the planned family:

- `geo` and `geo3` may expose the same dimension-neutral operation name when
  their accepted geometry types make normal calls unambiguous;
- shared names must not rely on accidental template overlap;
- constraints must be checked for cross-dimension matching;
- non-function names exported by both package modules require an explicit
  collision strategy.

This coexistence rule must be tested with a compile-only `geo` + `geo3`
design model before the v2 API freeze.

## Naming grammar under review

### Dimension-bearing geometry types

A geometry type whose semantics inherently encode coordinate dimension should
make that dimension visible in its canonical public name.

Already explicit in v1:

~~~text
Point2
Vector2
Segment2
Bounds2
~~~

Initial ADR-0019 rename candidates:

~~~text
PolylineView     -> Polyline2View
LinearRingView   -> LinearRing2View
PolygonView      -> Polygon2View
~~~

Corresponding old names should normally remain deprecated aliases during v2
when this is source-compatible and unambiguous.

A similarly named 3D type is not automatically justified merely for symmetry.
The mathematical representation contract must also transfer coherently.

In particular, a possible `Polygon3View` requires an explicit decision about
planarity and polygon semantics rather than being inferred mechanically from
`Polygon2View`.

### Dimension-neutral operations

Operations should normally keep mathematical operation names rather than gain
a `2` suffix.

Examples under review include:

~~~text
distance
squaredDistance
tryBounds
tryNearestPoint
orientation
segmentIntersectionKind
~~~

A future 3D API may use the same operation name where the mathematical concept
and overload behaviour remain coherent.

### Dimension-sensitive result and policy types

Names that are not themselves dimension-tagged require separate review when a
corresponding `geo3-d` symbol could also be exported.

Examples include:

~~~text
AreaScalar
MetricScalar
IntersectionScalar
Orientation
SegmentIntersectionKind
PointPolygonLocation
RingValidationIssue
RingValidationResult
PolygonValidationIssue
PolygonValidationResult
~~~

The audit must distinguish:

- genuinely dimension-independent vocabulary;
- same vocabulary but dimension-specific semantics;
- names that would collide under simultaneous package imports;
- names that should become dimension-qualified;
- names for which no 3D analogue is justified.

## UFCS receiver rule

For each free-function family, identify the mathematical object being operated
on and use it as the first parameter where practical.

This is not an absolute rule for symmetric operations such as point-to-point
distance, but related asymmetric operations should not choose different
receivers without reason.

Known review case:

~~~d
tryNearestPoint(segment, point, result);
tryPointSegmentDistance(point, segment, result);
~~~

Candidate v2 normalization:

~~~d
tryNearestPoint(segment, point, result);
tryPointSegmentDistance(segment, point, result);
~~~

The second form is not yet an accepted v2 decision.

Before changing it, verify:

- overload resolution;
- named-argument compatibility;
- deprecated v1 forwarding overload feasibility;
- UFCS behaviour;
- `geo3-d` analogue.

## Orientation review

`orientation` remains a dedicated decision area.

The v1 implementation exposes four concrete overloads corresponding to the
currently supported robust scalar domains.

The v2 review must resolve independently:

- operation name;
- 2D arity;
- plausible 3D arity;
- 2D result type;
- possible 3D result type;
- result-value vocabulary;
- robustness requirements;
- cross-library overload behaviour.

The 2D predicate must not be conflated with vector cross product merely to
obtain superficial 2D/3D symmetry.

Current v1 `Orientation` values are:

~~~text
right       = -1
collinear   =  0
left        = +1
~~~

Those values are part of the audited v1 contract.

## Decision vocabulary

Each public declaration eventually receives one of the following dispositions:

| Status | Meaning |
|---|---|
| `KEEP` | canonical v1 form remains canonical in v2 |
| `RENAME` | canonical v2 name changes |
| `REORDER` | canonical argument order changes |
| `SEMANTIC-REVIEW` | mathematical/API semantics require a dedicated decision |
| `COMPAT-ALIAS` | deprecated v1 name aliases the canonical v2 declaration |
| `COMPAT-FORWARDER` | deprecated v1 callable forwards to canonical v2 implementation |
| `2D-ONLY` | concept intentionally has no corresponding `geo3-d` API |
| `SHARED-FAMILY` | plausible corresponding operation/type family exists in `geo3-d` |
| `COLLISION-REVIEW` | simultaneous `geo` / `geo3` imports require explicit treatment |
| `TBD` | audit decision not yet made |

A declaration may need more than one label during analysis, for example
`RENAME + COMPAT-ALIAS + SHARED-FAMILY`.

## Family review order

The audit proceeds by coherent API family rather than source-file order:

1. scalar and computation policies;
2. core values: point, vector, segment, bounds;
3. variable-size views;
4. conversion and quantisation;
5. metric operations;
6. bounds operations;
7. orientation;
8. segment intersection;
9. area;
10. point-in-polygon;
11. topology validation;
12. simplification;
13. package-level coexistence and compatibility.

For every shared candidate, write down a plausible `geo3-d` signature before
accepting the v2 decision.

## Family decision 1 — scalar policy and core values

### Scope of this decision

This family review covers:

~~~text
isGeoScalar
Point2
Vector2
Segment2
Bounds2
~~~

and every public member of the four core geometry types.

The computation-policy aliases:

~~~text
AreaScalar
MetricScalar
IntersectionScalar
~~~

are deliberately not decided here.

Although all three map input scalars to computation/result scalars, their
contracts belong to different algorithm families and need not have identical
2D/3D treatment. They are reviewed with area, metric, and intersection
respectively.

### Dimension-bearing core type grammar

Accepted canonical grammar:

~~~text
geo-d       geo3-d
-----       ------
Point2      Point3
Vector2     Vector3
Segment2    Segment3
Bounds2     Bounds3
~~~

`Point2`, `Vector2`, `Segment2`, and `Bounds2` already satisfy the v2
dimensional naming rule.

Their canonical names therefore remain unchanged.

No compatibility alias is required because no rename occurs.

Disposition:

~~~text
Point2      KEEP + SHARED-FAMILY
Vector2     KEEP + SHARED-FAMILY
Segment2    KEEP + SHARED-FAMILY
Bounds2     KEEP + SHARED-FAMILY
~~~

Plausible `geo3-d` counterparts:

~~~d
struct Point3(T);
struct Vector3(T);
struct Segment3(T);
struct Bounds3(T);
~~~

These signatures describe the intended naming family only. They do not admit
`geo3-d` functionality into `geo-d`.

### No public N-dimensional abstraction

The shared naming family does not imply a public abstraction such as:

~~~text
Point!(N, T)
Vector!(N, T)
Segment!(N, T)
Bounds!(N, T)
~~~

for v2.

The existing types model concrete geometry concepts directly. Introducing a
public dimension template would create a new abstraction and compatibility
surface without a demonstrated consumer requirement.

The v2 family therefore uses parallel concrete types rather than exposing an
N-dimensional public foundation.

### Point and vector member grammar

`Point2` and `Vector2` retain their existing coordinate/component accessors:

~~~text
Point2.x
Point2.y

Vector2.x
Vector2.y
~~~

The corresponding plausible 3D grammar is:

~~~text
Point3.x
Point3.y
Point3.z

Vector3.x
Vector3.y
Vector3.z
~~~

`isFinite` remains the common member name in both dimensions.

Constructors follow the same coordinate ordering:

~~~d
Point2(T x, T y);
Point3(T x, T y, T z);

Vector2(T x, T y);
Vector3(T x, T y, T z);
~~~

### Affine algebra

The v1 distinction between points and vectors is retained.

For both dimensions the intended algebraic family is:

~~~text
Point + Vector  -> Point
Vector + Point  -> Point
Point - Vector  -> Point
Point - Point   -> Vector

Vector + Vector -> Vector
Vector - Vector -> Vector
-Vector         -> Vector
Vector * scalar -> Vector
scalar * Vector -> Vector
Vector / scalar -> Vector where the scalar contract permits it
~~~

Operations that are intentionally invalid in 2D remain conceptually invalid
in 3D:

~~~text
Point + Point
-Point
Point * scalar
scalar * Point
Point / scalar
~~~

The existing operator names and operand ordering therefore remain canonical.

Disposition for the public `Point2` and `Vector2` constructor, accessor,
`isFinite`, `opBinary`, `opBinaryRight`, `opUnary`, and `opOpAssign`
declarations:

~~~text
KEEP + SHARED-FAMILY
~~~

No deprecated compatibility declaration is required.

### Segment grammar

`Segment2` remains a stored pair of points with endpoint names:

~~~text
a
b
~~~

The corresponding plausible 3D representation is:

~~~d
struct Segment3(T)
{
    this(Point3!T a, Point3!T b);
    Point3!T a() const;
    Point3!T b() const;
    bool isFinite() const;
}
~~~

The endpoint names are intentionally dimension-neutral and remain canonical.

Disposition for `Segment2` and all its public members:

~~~text
KEEP + SHARED-FAMILY
~~~

### Bounds grammar

`Bounds2` remains the axis-aligned 2D bounds type.

The corresponding plausible 3D type is `Bounds3`.

The following member vocabulary transfers naturally:

~~~text
empty
min
max
isFinite
tryFromPoint
tryFromMinMax
tryExtend
extend
contains
intersects
opEquals
~~~

For example, a plausible 3D construction family is:

~~~d
static bool tryFromPoint(
    Point3!T point,
    out Bounds3 result
);

static bool tryFromMinMax(
    Point3!T minimum,
    Point3!T maximum,
    out Bounds3 result
);
~~~

The dimensional difference is represented by `Point2` versus `Point3` and
`Bounds2` versus `Bounds3`; the operation vocabulary itself remains the same.

Disposition for `Bounds2` and all its public members:

~~~text
KEEP + SHARED-FAMILY
~~~

### Scalar-domain trait

The v1 trait:

~~~d
isGeoScalar!T
~~~

describes the scalar domain accepted by the core geometry model:

~~~text
int
long
float
double
real
~~~

That policy is not intrinsically two-dimensional.

The canonical `geo-d` v2 name therefore remains:

~~~text
isGeoScalar
~~~

Disposition:

~~~text
KEEP + COLLISION-REVIEW
~~~

No `isGeo2Scalar` rename is introduced merely to manufacture dimensional
symmetry.

A future `geo3-d` implementation is expected to define an equivalent scalar
policy for its core geometry. However, ADR-0019 does not require that policy
to be exposed as a second independent package-level symbol named
`isGeoScalar`.

That package-export question is deferred to the simultaneous
`import geo; import geo3;` coexistence review.

The important distinction is:

~~~text
shared scalar policy
    !=
mandatory duplicate package-level policy symbol
~~~

This avoids prematurely introducing either:

- artificial names such as `isGeo2Scalar` / `isGeo3Scalar`;
- a new common dependency solely to host one trait; or
- an avoidable package-level name collision.

### Result of family decision 1

Accepted:

~~~text
Point2                   KEEP + SHARED-FAMILY
Point2 public members    KEEP + SHARED-FAMILY

Vector2                  KEEP + SHARED-FAMILY
Vector2 public members   KEEP + SHARED-FAMILY

Segment2                 KEEP + SHARED-FAMILY
Segment2 public members  KEEP + SHARED-FAMILY

Bounds2                  KEEP + SHARED-FAMILY
Bounds2 public members   KEEP + SHARED-FAMILY

isGeoScalar              KEEP + COLLISION-REVIEW
~~~

No v1 compatibility layer is required for these declarations because none of
their canonical v2 names or signatures changes in this family decision.

## Family decision 2 — variable-size geometry views

### Scope of this decision

This review covers:

~~~text
PolylineView
LinearRingView
PolygonView
~~~

and every public member of those view types.

All three v1 names omit the dimension even though their stored geometry is
explicitly based on `Point2`, `Segment2`, or other 2D geometry types.

The canonical v2 names therefore make the dimension explicit.

### Polyline view

Accepted canonical rename:

~~~text
PolylineView -> Polyline2View
~~~

The representation itself transfers directly to three dimensions:

~~~d
struct Polyline2View(T);
struct Polyline3View(T);
~~~

Both represent a non-owning read-only view over an ordered sequence of points.

The member vocabulary remains dimension-neutral:

~~~text
this
length
empty
segmentCount
segment
opIndex
~~~

The dimensional difference appears in the point and segment types returned
by those operations:

~~~text
Polyline2View -> Point2 / Segment2
Polyline3View -> Point3 / Segment3
~~~

Disposition of the type:

~~~text
RENAME + COMPAT-ALIAS + SHARED-FAMILY
~~~

Disposition of its public members:

~~~text
KEEP + SHARED-FAMILY
~~~

The v1 name remains available throughout v2 as a deprecated alias of the
canonical type:

~~~d
deprecated("Use Polyline2View")
alias PolylineView = Polyline2View;
~~~

The exact D declaration form remains subject to implementation verification,
but there must be only one underlying implementation.

Member compatibility follows automatically through the type alias; separate
deprecated member wrappers are neither needed nor desired.

### Linear-ring view

Accepted canonical rename:

~~~text
LinearRingView -> LinearRing2View
~~~

The representation contract is an ordered cyclic point sequence with implicit
closure.

That representation itself is not inherently restricted to 2D. A
corresponding 3D cyclic polyline is coherent:

~~~d
struct LinearRing2View(T);
struct LinearRing3View(T);
~~~

The corresponding member family remains:

~~~text
this
length
empty
segmentCount
segment
opIndex
~~~

and naturally changes only its dimensional point/segment types.

This decision does not claim that every algorithm currently accepting a
2D linear ring has a meaningful 3D analogue.

In particular, signed area, polygon topology, winding interpretation, and
point-in-polygon semantics remain separate algorithm-family decisions.

Disposition of the type:

~~~text
RENAME + COMPAT-ALIAS + SHARED-FAMILY
~~~

Disposition of its public members:

~~~text
KEEP + SHARED-FAMILY
~~~

Compatibility:

~~~d
deprecated("Use LinearRing2View")
alias LinearRingView = LinearRing2View;
~~~

Again, member compatibility is inherited through the alias rather than
implemented independently.

### Polygon view

Accepted canonical 2D rename:

~~~text
PolygonView -> Polygon2View
~~~

The v1 representation is specifically a polygonal planar-region model:

~~~text
ring 0      exterior boundary
ring 1..n   interior boundaries / holes
~~~

Those semantics are stronger than merely storing a cyclic sequence of
vertices.

A mechanical type:

~~~d
struct Polygon3View(T)
{
    // array of LinearRing3View!T
}
~~~

would leave essential geometric questions undefined, including:

- whether every ring must be planar;
- whether all rings must lie in one common plane;
- how that plane is represented or inferred;
- how non-coplanarity is handled;
- how exterior/interior ring containment is defined;
- what orientation means relative to the embedding plane;
- what area and point classification mean.

Consequently, v2 does not manufacture `Polygon3View` merely for naming
symmetry.

The current polygon representation remains a 2D concept:

~~~text
Polygon2View    canonical geo-d type
Polygon3View    not admitted by this migration
~~~

A future `geo3-d` planar polygon or planar-surface abstraction may be designed
if a concrete consumer requires it, but that design must define its
planarity/embedding contract independently.

Disposition of the type:

~~~text
RENAME + COMPAT-ALIAS + 2D-ONLY
~~~

Disposition of its existing members:

~~~text
KEEP + 2D-ONLY
~~~

The member vocabulary remains canonical for the 2D type:

~~~text
this
length
empty
holeCount
opIndex
exterior
hole
~~~

Compatibility:

~~~d
deprecated("Use Polygon2View")
alias PolygonView = Polygon2View;
~~~

As with the other view aliases, existing v1 member calls remain available
through that alias rather than through duplicate member implementations.

### Ownership and lifetime

The dimensional rename does not change the established ownership model.

All canonical v2 view types remain:

- non-owning;
- read-only through the view;
- aliases of caller-owned backing storage;
- allocation-free to construct and copy;
- subject to the established DIP1000 lifetime constraints.

The migration must not introduce owning storage or deep copying merely to make
the 2D and 3D names look alike.

### Result of family decision 2

Accepted:

~~~text
PolylineView
    -> Polyline2View
    RENAME + COMPAT-ALIAS + SHARED-FAMILY
    plausible geo3-d analogue: Polyline3View

LinearRingView
    -> LinearRing2View
    RENAME + COMPAT-ALIAS + SHARED-FAMILY
    plausible geo3-d analogue: LinearRing3View

PolygonView
    -> Polygon2View
    RENAME + COMPAT-ALIAS + 2D-ONLY
    no mechanical Polygon3View
~~~

Public member names remain canonical.

For the two shared families, plausible 3D member signatures follow the same
structure with `Point3` and `Segment3`.

For `Polygon2View`, no corresponding `geo3-d` signature is required because
the v1 polygon representation is not accepted as a shared 2D/3D concept.

## Family decision 3 — conversion and quantisation

### Scope of this decision

This review covers the complete public `geo.convert` surface:

~~~text
tryConvert
rounded
floored
ceiled
truncated
~~~

The v1 surface contains:

- three `tryConvert` overloads for point, vector, and segment;
- two overloads each for `rounded`, `floored`, `ceiled`, and `truncated`.

That is 11 public declarations.

### General dimensional rule

Scalar conversion and coordinate-wise quantisation are not intrinsically
two-dimensional operations.

Their dimensional behaviour is determined by the geometry type on which they
operate.

The canonical operation names therefore remain dimension-neutral:

~~~text
tryConvert
rounded
floored
ceiled
truncated
~~~

No `2` or `3` suffix is added to these operation names.

### Checked conversion

The canonical v2 point family remains structurally:

~~~d
bool tryConvert(To, From)(
    Point2!From source,
    out Point2!To result
);

bool tryConvert(To, From)(
    Point3!From source,
    out Point3!To result
);
~~~

Likewise for vectors:

~~~d
bool tryConvert(To, From)(
    Vector2!From source,
    out Vector2!To result
);

bool tryConvert(To, From)(
    Vector3!From source,
    out Vector3!To result
);
~~~

and segments:

~~~d
bool tryConvert(To, From)(
    Segment2!From source,
    out Segment2!To result
);

bool tryConvert(To, From)(
    Segment3!From source,
    out Segment3!To result
);
~~~

The conversion semantics remain component-wise and use the same scalar-domain
policy.

No mixed-dimension conversion is introduced by this family decision.

In particular, this decision does not create operations such as:

~~~text
Point2 -> Point3
Point3 -> Point2
Vector2 -> Vector3
Vector3 -> Vector2
~~~

Such dimensional transformations would require independent semantics and a
consumer requirement.

### UFCS and parameter order

The existing argument order is canonical:

~~~d
tryConvert(source, result);
source.tryConvert(result);
~~~

The source geometry is the natural UFCS receiver.

The public parameter names:

~~~text
source
result
~~~

also remain canonical.

No reorder or compatibility forwarder is required.

### Quantisation

The four quantisation operations retain the existing property-style API:

~~~d
point.rounded
point.floored
point.ceiled
point.truncated

vector.rounded
vector.floored
vector.ceiled
vector.truncated
~~~

The plausible 3D family is identical in structure:

~~~d
Point3!T rounded(Point3!T value);
Vector3!T rounded(Vector3!T value);

Point3!T floored(Point3!T value);
Vector3!T floored(Vector3!T value);

Point3!T ceiled(Point3!T value);
Vector3!T ceiled(Vector3!T value);

Point3!T truncated(Point3!T value);
Vector3!T truncated(Vector3!T value);
~~~

The scalar type remains unchanged by quantisation, exactly as in v1.

The existing restriction to floating-point geometry also remains conceptually
shared between dimensions.

### No speculative surface expansion

v1 does not expose component-wise quantisation for `Segment2`.

The v2 migration therefore does not add corresponding segment quantisation
merely for symmetry.

Similarly, this family decision does not add conversion overloads for bounds,
polylines, rings, polygons, or other aggregate geometry.

Such additions remain consumer-driven and research-gated.

### Cross-library overload behaviour

A future `geo3-d` may expose the same operation names.

Normal 2D and 3D calls remain distinguishable by their geometry argument:

~~~text
Point2  versus Point3
Vector2 versus Vector3
Segment2 versus Segment3
~~~

The intended overload families therefore remain disjoint by geometry type.

The later package-coexistence phase must still validate simultaneous:

~~~d
import geo;
import geo3;
~~~

with compile-only tests, but no naming change is required by this family.

### Result of family decision 3

All 11 existing v1 declarations retain their canonical operation name,
argument order, parameter naming, and semantics.

Disposition:

~~~text
tryConvert(Point2)       KEEP + SHARED-FAMILY
tryConvert(Vector2)      KEEP + SHARED-FAMILY
tryConvert(Segment2)     KEEP + SHARED-FAMILY

rounded(Point2)          KEEP + SHARED-FAMILY
rounded(Vector2)         KEEP + SHARED-FAMILY

floored(Point2)          KEEP + SHARED-FAMILY
floored(Vector2)         KEEP + SHARED-FAMILY

ceiled(Point2)           KEEP + SHARED-FAMILY
ceiled(Vector2)          KEEP + SHARED-FAMILY

truncated(Point2)        KEEP + SHARED-FAMILY
truncated(Vector2)       KEEP + SHARED-FAMILY
~~~

No v1 compatibility declaration is required because the canonical v2 callable
surface is unchanged.

## Family decision 4 — metric operations

### Scope of this decision

This review covers the complete public `geo.metric` surface:

~~~text
MetricScalar
distance
squaredDistance
segmentLength
polylineLength
tryNearestPoint
tryPointSegmentDistance
~~~

That is seven public declarations.

### Metric scalar policy

`MetricScalar!T` separates geometry storage precision from metric computation
precision.

The v1 policy is:

~~~text
int     -> double
long    -> double
float   -> double
double  -> double
real    -> real
~~~

That policy is not intrinsically two-dimensional.

The canonical `geo-d` v2 name therefore remains:

~~~text
MetricScalar
~~~

## Family decision 5 — bounds computation

### Scope of this decision

This review covers the four public `tryBounds` overloads:

~~~text
tryBounds(Segment2)
tryBounds(PolylineView)
tryBounds(LinearRingView)
tryBounds(PolygonView)
~~~

Following Family decision 2, the canonical v2 view spellings are:

~~~text
Polyline2View
LinearRing2View
Polygon2View
~~~

The operation itself remains named `tryBounds`.

### Operation naming and UFCS

Axis-aligned bounds computation is meaningful independently of coordinate
dimension.

The operation name therefore remains dimension-neutral:

~~~text
tryBounds
~~~

All existing overloads already place the geometry being bounded first:

~~~d
tryBounds(geometry, result);
geometry.tryBounds(result);
~~~

That geometry is the natural UFCS receiver.

No argument reorder is required.

The public output parameter name:

~~~text
result
~~~

also remains canonical.

### Segment bounds

The canonical 2D form remains structurally:

~~~d
bool tryBounds(T)(
    Segment2!T segment,
    out Bounds2!T result
);
~~~

The corresponding plausible `geo3-d` form is:

~~~d
bool tryBounds(T)(
    Segment3!T segment,
    out Bounds3!T result
);
~~~

The algorithmic contract transfers directly: every stored endpoint
participates in the component-wise axis-aligned bounds.

Disposition:

~~~text
KEEP + SHARED-FAMILY
~~~

### Polyline bounds

Following the view rename, the canonical v2 2D form is:

~~~d
bool tryBounds(T)(
    scope Polyline2View!T polyline,
    out Bounds2!T result
);
~~~

The plausible 3D form is:

~~~d
bool tryBounds(T)(
    scope Polyline3View!T polyline,
    out Bounds3!T result
);
~~~

Every stored point contributes component-wise to the corresponding
axis-aligned bounds.

Disposition:

~~~text
KEEP + SHARED-FAMILY
~~~

The v1 spelling `PolylineView` remains source-compatible through the deprecated
type alias. A separate deprecated `tryBounds` overload is therefore neither
required nor desirable.

### Linear-ring bounds

Following the view rename, the canonical v2 2D form is:

~~~d
bool tryBounds(T)(
    scope LinearRing2View!T ring,
    out Bounds2!T result
);
~~~

The plausible 3D form is:

~~~d
bool tryBounds(T)(
    scope LinearRing3View!T ring,
    out Bounds3!T result
);
~~~

Bounds depend only on the stored vertices. The implicit closing segment adds
no new extrema in either dimension.

This operation therefore transfers coherently even though many other
ring-related algorithms remain dimension-sensitive.

Disposition:

~~~text
KEEP + SHARED-FAMILY
~~~

Compatibility of the v1 `LinearRingView` spelling is supplied by the
deprecated type alias.

### Polygon bounds

Following Family decision 2, the canonical 2D form becomes:

~~~d
bool tryBounds(T)(
    scope Polygon2View!T polygon,
    out Bounds2!T result
);
~~~

The operation itself remains canonical and unchanged.

However, Family decision 2 deliberately does not admit a mechanical
`Polygon3View`.

Consequently this particular overload has no corresponding `geo3-d`
signature in the current API-family model.

Disposition:

~~~text
KEEP + 2D-ONLY
~~~

This does not imply that axis-aligned bounds of future 3D surface or solid
types are invalid concepts.

It means only that no hypothetical 3D geometry type is introduced merely to
mirror the existing 2D polygon overload.

A future `geo3-d` surface or solid representation may receive its own
`tryBounds` overload when such a representation is independently designed and
consumer-justified.

Compatibility of the v1 `PolygonView` spelling is supplied by its deprecated
alias to `Polygon2View`.

### Failure and representation semantics

The v2 migration does not change the established bounds contract.

In particular:

- computation remains in the geometry's scalar domain;
- no coordinate conversion is performed;
- no topology validation is performed;
- no allocation is introduced;
- NaN rejection remains transactional;
- permitted infinities continue to participate normally;
- empty variable-size geometry continues to produce `Bounds2.init`;
- invalid-but-representable rings and polygons may still have representation
  bounds.

Corresponding 3D shared-family overloads should preserve the same principles
with `Point3` and `Bounds3`.

### No speculative overload expansion

The migration does not add new `tryBounds` overloads merely for completeness.

In particular, it does not add:

~~~text
tryBounds(Point2)
tryBounds(Bounds2)
~~~

or new aggregate geometry categories.

Existing point-to-bounds construction remains available through
`Bounds2.tryFromPoint`.

New overloads remain consumer-driven.

Accepted:

~~~text

    KEEP + SHARED-FAMILY
    geo3-d: tryBounds(Segment3, Bounds3)

tryBounds(Polyline2View)
    KEEP + SHARED-FAMILY
    geo3-d: tryBounds(Polyline3View, Bounds3)
    v1 view spelling preserved by alias

tryBounds(LinearRing2View)
    KEEP + SHARED-FAMILY
    geo3-d: tryBounds(LinearRing3View, Bounds3)
    v1 view spelling preserved by alias

tryBounds(Polygon2View)
    KEEP + 2D-ONLY
    no Polygon3View analogue admitted
    v1 view spelling preserved by alias
~~~

## Family decision 6 — orientation predicate

### Scope of this decision

This review covers the complete public `geo.orientation` surface:

~~~text
Orientation
Orientation.right
Orientation.collinear
Orientation.left

orientation(Point2!int,    Point2!int,    Point2!int)
orientation(Point2!long,   Point2!long,   Point2!long)
orientation(Point2!double, Point2!double, Point2!double)
orientation(Point2!float,  Point2!float,  Point2!float)
~~~

That is eight public declarations.

### Mathematical family

The 2D orientation predicate classifies a third point relative to the
oriented line through the first two points:

~~~text
right
collinear
left
~~~

A corresponding 3D orientation predicate is not the orientation of three
arbitrary 3D points.

The ordinary 3D orientation predicate uses four points and classifies the
fourth point relative to the oriented plane defined by the first three:

~~~text
negative
coplanar
positive
~~~

The shared operation family is therefore:

~~~text
2D: orientation(a, b, c)
3D: orientation(a, b, c, d)
~~~

The common operation name is intentional.

The dimensional difference is expressed by point type, arity, and result
type rather than by names such as `orientation2` and `orientation3`.

### Result-type naming

The v1 result type:

~~~text
Orientation
~~~

is semantically 2D because its public vocabulary is:

~~~text
right
collinear
left
~~~

Keeping `Orientation` in `geo-d` while introducing `Orientation3` in
`geo3-d` would make the type-family naming asymmetric.

Exporting an independent `Orientation` from both packages would instead
create an avoidable package-level type-name collision.

The canonical v2 2D result type is therefore:

~~~text
Orientation2
~~~

with the plausible future 3D counterpart:

~~~text
Orientation3
~~~

Disposition of the type:

~~~text
RENAME + COMPAT-ALIAS + SHARED-FAMILY
~~~

### Orientation2 value contract

The existing 2D values remain exactly:

~~~text
Orientation2.right       = -1
Orientation2.collinear   =  0
Orientation2.left        = +1
~~~

No sign convention changes during the rename.

The existing v1 initialization contract also remains unchanged:

~~~text
Orientation2.init == Orientation2.right
~~~

This is deliberately preserved even though it is a valid non-neutral default.

The declaration order and explicit values of `Orientation2` must therefore
preserve that behaviour.

### v1 result-type compatibility

The v1 spelling remains throughout v2 as a deprecated alias:

~~~d
deprecated("Use Orientation2")
alias Orientation = Orientation2;
~~~

Consequently existing forms such as:

~~~d
Orientation value;
Orientation.left;
Orientation.collinear;
Orientation.right;
~~~

remain source-compatible during the v2 migration, subject to the expected
deprecation diagnostic.

There is only one underlying enum implementation.

### 3D result vocabulary

A plausible `geo3-d` orientation-result vocabulary is:

~~~text
Orientation3.negative    -> determinant sign -1
Orientation3.coplanar    -> determinant sign  0
Orientation3.positive    -> determinant sign +1
~~~

This follows the geometry of the four-point 3D orientation predicate rather
than importing the 2D terms `left` and `right` into three dimensions.

The exact declaration order and therefore `Orientation3.init` are not frozen
by this `geo-d` audit.

They remain a `geo3-d` design decision when that library is introduced.

This distinction is intentional:

~~~text
shared predicate family
    does not imply
identical result-member vocabulary
~~~

### Existing 2D overload family

The four v1 overloads remain the canonical supported scalar backends:

~~~text
int
long
float
double
~~~

`real` remains unsupported until a suitable robust backend exists.

The v2 migration does not replace the existing overload family with a broad
generic template merely for syntactic compactness.

That would alter overload/constraint behaviour without a demonstrated
correctness or consumer benefit.

Each existing overload changes only its canonical result-type spelling:

~~~text
Orientation -> Orientation2
~~~

The operation name, point order, scalar domain, robustness contract, and
parameter names remain unchanged.

Disposition of all four `orientation` callables:

~~~text
KEEP + SHARED-FAMILY
~~~

Compatibility of the old return-type spelling is provided by the deprecated
`Orientation` alias.

### Parameter order and UFCS

The canonical 2D order remains:

~~~d
orientation(a, b, c);
a.orientation(b, c);
~~~

The first two points define the directed line and the third point is
classified relative to it.

The plausible 3D form is:

~~~d
orientation(a, b, c, d);
a.orientation(b, c, d);
~~~

where the first three points define an oriented plane and the fourth is
classified relative to that plane.

No argument reorder is justified.

Parameter names:

~~~text
a
b
c
~~~

remain canonical in 2D.

A plausible 3D overload extends the same sequence with:

~~~text
d
~~~

### Cross-library overload structure

The desired simultaneous package model is structurally:

~~~d
// geo
Orientation2 orientation(
    Point2 ... a,
    Point2 ... b,
    Point2 ... c
);

// geo3
Orientation3 orientation(
    Point3 ... a,
    Point3 ... b,
    Point3 ... c,
    Point3 ... d
);
~~~

The overload families differ in both geometry type and arity.

This is a stronger distinction than relying only on overlapping template
constraints.

The final package-coexistence phase must nevertheless include compile-only
tests using simultaneous:

~~~d
import geo;
import geo3;
~~~

### No three-point arbitrary-3D orientation overload

This migration does not introduce:

~~~d
orientation(
    Point3 a,
    Point3 b,
    Point3 c
);
~~~

as a direct analogue of the 2D predicate.

Three arbitrary 3D points determine a plane when non-collinear, but they do
not by themselves provide the same global left/right predicate as three
points in an oriented 2D coordinate plane.

Any future orientation of coplanar 3D geometry requires an explicit plane or
projection/orientation contract and is a separate API design problem.

### Orientation is not cross product

The `orientation` predicate remains distinct from vector cross product.

In 2D the determinant underlying orientation is scalar-valued.

In 3D vector cross product is vector-valued, while four-point orientation is
a scalar sign predicate.

The two concepts must not be merged merely to create superficial dimensional
symmetry.

### Result of family decision 6

Accepted:

~~~text
Orientation
    -> Orientation2
    RENAME + COMPAT-ALIAS + SHARED-FAMILY
    plausible geo3-d counterpart: Orientation3

Orientation.right
    -> Orientation2.right
    value -1 preserved
    3D semantic sign analogue: Orientation3.negative

Orientation.collinear
    -> Orientation2.collinear
    value 0 preserved
    3D degeneracy analogue: Orientation3.coplanar

Orientation.left
    -> Orientation2.left
    value +1 preserved
    3D semantic sign analogue: Orientation3.positive

orientation(Point2, Point2, Point2)
    KEEP + SHARED-FAMILY
    plausible geo3-d family:
        orientation(Point3, Point3, Point3, Point3)
~~~

The four existing scalar-specific overloads remain distinct public
declarations.

## Family decision 7 — segment intersection

### Scope of this decision

This review covers the complete public `geo.intersection` surface:

~~~text
SegmentIntersectionKind
SegmentIntersectionKind.none
SegmentIntersectionKind.point
SegmentIntersectionKind.overlap

IntersectionScalar

segmentIntersectionKind
trySegmentIntersectionPoint
trySegmentIntersectionOverlap
~~~

That is eight public declarations.

### Dimensional geometry of segment intersection

The intersection set of two closed line segments has the same possible
topological dimensions in 2D and 3D:

~~~text
empty
single point
positive-length segment
~~~

In 3D, two non-parallel supporting lines may additionally be skew.

That does not require a new public intersection category: skew segments have
an empty intersection and therefore classify as `none`.

Consequently the existing public topology:

~~~text
none
point
overlap
~~~

is dimension-independent for segment-versus-segment intersection.

### SegmentIntersectionKind

The v1 enum:

~~~d
enum SegmentIntersectionKind : ubyte
{
    none,
    point,
    overlap
}
~~~

already describes intersection-set topology rather than 2D orientation.

Its canonical v2 name therefore remains:

~~~text
SegmentIntersectionKind
~~~

No `SegmentIntersectionKind2` rename is introduced.

A plausible 3D segment-intersection API needs the same semantic states.

However, this audit does not yet require `geo3` to export an independent
second declaration named `SegmentIntersectionKind`.

Doing so could create a package-level collision under:

~~~d
import geo;
import geo3;
~~~

Disposition of the enum and its three values:

~~~text
KEEP + COLLISION-REVIEW
~~~

The package-coexistence phase must determine whether the shared vocabulary is:

- exposed from only one appropriate package-level location;
- re-exported from some future common dependency justified by broader need; or
- otherwise structured without ambiguous simultaneous imports.

This audit deliberately does not introduce a common library merely to solve
one future name collision.

### Enum value semantics

The semantic contract remains exactly:

~~~text
SegmentIntersectionKind.none
    intersection set is empty

SegmentIntersectionKind.point
    intersection set contains exactly one geometric point

SegmentIntersectionKind.overlap
    intersection set is a segment of positive geometric length
~~~

These meanings transfer unchanged to `Segment3`.

No additional public state such as:

~~~text
skew
~~~

is introduced.

Skewness describes the relative supporting-line geometry in 3D, not a fourth
intersection-set topology. For closed segment intersection it therefore maps
to `none`.

### IntersectionScalar

`IntersectionScalar!T` describes the scalar used for constructed unique
intersection points.

The current policy is:

~~~text
int     -> double
long    -> double
float   -> double
double  -> double
~~~

and `real` is deliberately unsupported.

That computation/construction policy is not intrinsically two-dimensional.

The canonical v2 name remains:

~~~text
IntersectionScalar
~~~

Disposition:

~~~text
KEEP + COLLISION-REVIEW
~~~

A plausible `geo3-d` implementation can use an equivalent policy for
constructed `Point3` intersections.

As with `MetricScalar`, whether `geo3` independently exports the same
package-level policy name is deferred to the package-coexistence review.

No artificial `Intersection2Scalar` / `Intersection3Scalar` names are
introduced merely to avoid that later decision.

### Intersection classification

The canonical v2 2D signature remains structurally:

~~~d
SegmentIntersectionKind segmentIntersectionKind(T)(
    Segment2!T first,
    Segment2!T second
);
~~~

A plausible 3D analogue is:

~~~d
SegmentIntersectionKind segmentIntersectionKind(T)(
    Segment3!T first,
    Segment3!T second
);
~~~

The operation is mathematically symmetric in `first` and `second`.

The existing parameter names and order remain canonical.

Disposition:

~~~text
KEEP + SHARED-FAMILY
~~~

The implementation strategy need not be shared.

In particular, the v1 2D classifier relies heavily on robust 2D orientation
predicates. A robust 3D classifier must use the predicates appropriate to
3D collinearity, coplanarity, and segment membership rather than mechanically
reuse the 2D implementation.

Shared API family therefore does not imply shared implementation.

### Unique intersection-point construction

The canonical 2D form remains:

~~~d
bool trySegmentIntersectionPoint(T, R)(
    Segment2!T first,
    Segment2!T second,
    out Point2!R point
);
~~~

The plausible 3D form is:

~~~d
bool trySegmentIntersectionPoint(T, R)(
    Segment3!T first,
    Segment3!T second,
    out Point3!R point
);
~~~

The operation succeeds only when the intersection set consists of exactly one
point.

That contract transfers directly to 3D.

A proper 3D point intersection may require a different robust construction
backend, but this does not require a different public operation name.

Disposition:

~~~text
KEEP + SHARED-FAMILY
~~~

The existing parameter names:

~~~text
first
second
point
~~~

remain canonical.

### Positive-length overlap construction

The canonical 2D form remains:

~~~d
bool trySegmentIntersectionOverlap(T)(
    Segment2!T first,
    Segment2!T second,
    out Segment2!T overlap
);
~~~

The plausible 3D form is:

~~~d
bool trySegmentIntersectionOverlap(T)(
    Segment3!T first,
    Segment3!T second,
    out Segment3!T overlap
);
~~~

A positive-length intersection of two straight segments requires them to lie
on the same supporting line in either dimension.

The result is therefore naturally another segment in the same coordinate
dimension.

Disposition:

~~~text
KEEP + SHARED-FAMILY
~~~

The existing parameter names:

~~~text
first
second
overlap
~~~

remain canonical.

### UFCS

The binary segment operations are symmetric.

The existing first parameter `first` is therefore an acceptable UFCS
receiver:

~~~d
first.segmentIntersectionKind(second);
first.trySegmentIntersectionPoint(second, point);
first.trySegmentIntersectionOverlap(second, overlap);
~~~

Choosing `first` as the syntactic receiver does not assign asymmetric
mathematical meaning.

No reorder is justified.

### Scalar backend

The v1 public segment-intersection surface supports:

~~~text
int
long
float
double
~~~

and deliberately excludes `real`.

The v2 migration preserves that public scalar-domain contract.

A future `geo3-d` implementation must justify its own robust predicate and
construction backend before promising the analogous scalar coverage.

The shared signatures in this audit are therefore API-family models, not an
instruction to implement unverified 3D arithmetic immediately.

### No speculative general intersection framework

This decision concerns only segment-versus-segment intersection.

It does not introduce:

- generalized variant-returning `intersection(...)`;
- line, ray, triangle, plane, surface, or solid intersection APIs;
- a generic intersection result hierarchy;
- new 3D geometry types beyond the already plausible `Point3` and `Segment3`.

Those remain consumer-driven and research-gated.

### Result of family decision 7

Accepted:

~~~text
SegmentIntersectionKind
    KEEP + COLLISION-REVIEW
    same none / point / overlap vocabulary applies in 3D

SegmentIntersectionKind.none
SegmentIntersectionKind.point
SegmentIntersectionKind.overlap
    KEEP + COLLISION-REVIEW

IntersectionScalar
    KEEP + COLLISION-REVIEW
    equivalent 3D construction policy plausible

segmentIntersectionKind
    KEEP + SHARED-FAMILY
    geo3-d: segmentIntersectionKind(Segment3, Segment3)

trySegmentIntersectionPoint
    KEEP + SHARED-FAMILY
    geo3-d:
        trySegmentIntersectionPoint(
            Segment3,
            Segment3,

        )

    KEEP + SHARED-FAMILY
    geo3-d:

~~~

No v1 compatibility declaration is required because no existing public name


### AreaScalar

`AreaScalar!T` defines the result scalar used by the current exact planar-area
operations.

The v1 policy is:

~~~text
int     -> double
long    -> double
float   -> double
double  -> double
~~~

and `real` remains deliberately unsupported.

The scalar policy itself is not intrinsically two-dimensional.

The canonical v2 name therefore remains:

~~~text
AreaScalar
~~~

Disposition:

~~~text
KEEP + COLLISION-REVIEW
~~~

No artificial names such as:

~~~text

~~~

are introduced merely to obtain dimensional symmetry.

A future `geo3-d` operation involving planar or surface area may require an
equivalent computation policy.

Whether such a future package independently exports `AreaScalar` is deferred
to the package-coexistence review.

### Signed area is a planar operation

The canonical v2 2D signature becomes:

~~~d
AreaScalar!T signedArea(T)(
    scope LinearRing2View!T ring
);
~~~

The operation name itself remains canonical.

Its sign has an explicitly planar meaning:

~~~text
counter-clockwise traversal  -> positive
clockwise traversal          -> negative
degenerate algebraic area    -> zero
~~~

That sign is defined relative to the orientation of the ambient 2D coordinate
plane.

A `LinearRing3View` by itself does not provide the information necessary to
define the same contract.

In particular, an arbitrary 3D ring does not establish:

- that all vertices are coplanar;
- which supporting plane should be used when they are not;
- which unit normal defines positive orientation;
- which projection, if any, defines clockwise versus counter-clockwise;
- how non-planarity is diagnosed.

Consequently v2 does not admit the mechanical analogue:

~~~d
signedArea(
    LinearRing3View
);
~~~

Disposition:

~~~text
KEEP + 2D-ONLY
~~~

Following Family decision 2, the old parameter spelling `LinearRingView`
remains source-compatible through its deprecated alias to `LinearRing2View`.

No separate `signedArea` compatibility overload is required.

### A future 3D planar-area API is a different contract

This decision does not state that area of 3D geometry is impossible.

A future `geo3-d` API may reasonably support concepts such as:

~~~text
area(planar geometry)
unsigned surface area
oriented area relative to an explicit normal
projected area relative to an explicit plane
~~~

but such operations require an explicit representation and semantic contract.

They must not be inferred from the existence of `LinearRing3View`.

This is especially important for signed area: without a selected orientation
of the supporting plane, reversing the normal reverses the sign.

Any such API remains consumer-driven and research-gated.

### Polygon area

Following Family decision 2, the canonical v2 signature becomes:

~~~d
AreaScalar!T polygonArea(T)(
    scope Polygon2View!T polygon
);
~~~

The operation remains role-based:

~~~text
ring 0      exterior magnitude added
ring 1..n   hole magnitudes subtracted
~~~

and ring traversal orientation does not define those roles.

Because `Polygon2View` itself is intentionally 2D-only and no mechanical
`Polygon3View` was admitted, `polygonArea` is likewise 2D-only in the current
API-family model.

Disposition:

~~~text
KEEP + 2D-ONLY
~~~

The deprecated `PolygonView -> Polygon2View` alias supplies v1 source
compatibility.

No callable compatibility wrapper is needed.

### UFCS

Both existing functions already use the geometry as their first parameter:

~~~d
ring.signedArea;
polygon.polygonArea;
~~~

Those are the intended 2D UFCS forms.

No argument reorder is justified.

### Exactness and scalar-domain contract

The v2 migration does not alter the established numerical contract.

For supported finite coordinates:

- determinant contributions are accumulated exactly;
- binary64 conversion occurs only at the documented final rounding point;
- `signedArea` remains algebraic rather than topological validation;
- `polygonArea` remains role-based rather than topology validation;
- non-finite coordinates retain the existing failure/result semantics.

The supported scalar domain remains:

~~~text
int
long
float
double
~~~

with `real` deferred.

### No speculative area expansion

This migration does not add:

- triangle-specific public area functions;
- polyline area;
- generic `area(geometry)` dispatch;
- 3D surface-area abstractions;
- normal-vector parameters;
- plane or projection types.

Those require independent consumers and research.

### Result of family decision 8

Accepted:

~~~text
AreaScalar
    KEEP + COLLISION-REVIEW
    possible future cross-dimensional computation policy
    package export remains TBD

signedArea(LinearRing2View)
    KEEP + 2D-ONLY
    no direct LinearRing3View analogue
    v1 view spelling preserved by deprecated alias

polygonArea(Polygon2View)
    KEEP + 2D-ONLY
    no Polygon3View analogue admitted
    v1 view spelling preserved by deprecated alias
~~~

The current operation classifies a `Point2` relative to the role-based planar
region represented by `Polygon2View`.

Following Family decision 2, that polygon model is deliberately 2D-only.

No mechanical `Polygon3View` is admitted.

Consequently point-in-polygon classification is also 2D-only in the current

~~~text
point relative to closed surface
point relative to solid
~~~

but those are different geometric relations with independently defined
representation and topology contracts.

They are not direct overloads of the existing planar polygon operation merely
because their result vocabularies might also contain words such as `inside`,
`boundary`, and `outside`.

~~~d
    location

~~~

This produces the natural UFCS form:

~~~d
polygon.tryClassifyPointInPolygon(
    point,
    location
);
~~~

The polygon is the region being queried and is therefore the intended
receiver.

No reorder is justified.

The public parameter names:

The function name and argument order do not change.

### Predicate and failure contract

The v2 migration preserves the existing classification contract.

Supported scalar types remain:

~~~text
int
long
float
double
~~~

`real` remains outside the robust predicate domain.

The operation continues to:

- reject a non-finite query point;
- reject non-finite stored polygon coordinates;
- reset `location` to `outside` on failure;
- classify an empty polygon as `outside` for a finite query;
- give boundary global precedence;
- use ring zero as exterior and later rings as interior rings;
- ignore ring orientation for role assignment;
- perform no topology validation or normalization;
- allocate no memory.

### Invalid polygon representations

The operation remains a classifier of the stored role-based representation.

It does not become an implicit polygon validator in v2.

Therefore behaviour for representations such as:

- self-intersecting rings;
- holes outside the exterior;
- overlapping holes;

continues to follow the documented deterministic classification semantics of
the existing implementation.

Topology validation remains a separate API family.


because no `Polygon3View` has been admitted.

Nor does it rename the current result type merely in anticipation of future
surface or solid containment APIs.

If `geo3-d` later acquires a concrete consumer for containment classification,
that API must first define what the containing object represents.


No existing public callable name or argument order changes in this family.

## Family decision 10 — topology validation

### Scope of this decision

This review covers the complete public `geo.topology_validation` surface.

It consists of:

~~~text

    6 enum members

RingValidationResult
    3 diagnostic fields
    valid

PolygonValidationIssue
    9 enum members

PolygonValidationResult
    6 diagnostic fields
    valid

validateRing

~~~

That is 32 public declarations.

### Ring validation and polygon validation are different dimensional cases

The public module currently contains two conceptually distinct validation
families.

Ring validation answers whether one cyclic polygonal chain is a valid simple
closed curve according to the library's representation contract.

Polygon validation additionally interprets several rings as the boundary
components of one planar polygonal region.

Those concepts must not be given identical dimensional treatment merely
because v1 stores them in one module.

### 3D linear-ring validity

Following Family decision 2, a plausible `LinearRing3View` is an ordered
cyclic sequence of `Point3` values with implicit closure.

It does not automatically represent a planar polygon boundary.

Nevertheless, the existing ring-validity conditions have coherent
three-dimensional counterparts:

~~~text
at least three stored vertices
finite coordinates
no zero-length implicit edge
no invalid non-adjacent point intersection
no positive-length edge overlap
~~~

These conditions define simplicity of the closed polygonal chain itself.

They do not require:

- coplanarity;
- a supporting plane;
- an area;
- clockwise/counter-clockwise orientation;
- polygon interior semantics.

A non-planar closed 3D ring may therefore be a valid simple cyclic curve.

That is intentional.

### RingValidationIssue

The existing ring issue vocabulary remains:

~~~text
none
tooFewVertices
nonFiniteCoordinate
zeroLengthEdge
selfIntersection
selfOverlap
~~~

Each state has the same representation-level meaning for a plausible
`LinearRing3View`.

The canonical type name therefore remains:

~~~text
RingValidationIssue
~~~

No `RingValidationIssue2` / `RingValidationIssue3` pair is introduced.

Disposition of the enum and all six enum values:

~~~text
KEEP + COLLISION-REVIEW
~~~

A future `geo3-d` ring validator plausibly needs the same vocabulary.

Whether both package surfaces independently export the same type name is
deferred to the package-coexistence review.

### RingValidationResult

The existing result contains only representation-level diagnostics:

~~~text

secondaryIndex
valid
~~~

The indices identify stored vertices or implicit ring edges and have the same
meaning for a 3D cyclic point sequence.

The canonical type name therefore remains:

~~~text
RingValidationResult
~~~

~~~text
KEEP + COLLISION-REVIEW
~~~

~~~text
    secondaryIndex == size_t.max
    valid          == true
~~~

No dimensional suffix is introduced merely to solve a future package-export

### Shared API does not imply shared algorithm

The 2D implementation may use robust 2D segment-intersection predicates and

A future 3D implementation must use correct `Segment3` intersection and
three-dimensional broad-phase logic.

The API-family decision therefore does not require source-level reuse of the
2D implementation.

It freezes only the corresponding public concept and naming grammar.

### Polygon validation remains planar

The existing polygon validator does considerably more than validate its

It assigns semantic roles:

~~~text

invalid interior ring
proper crossing between rings
positive-length boundary overlap
multiple distinct contacts
interior ring outside exterior
nested interior rings
disconnected polygon interior
~~~

Those diagnostics are part of the planar region topology represented by
`Polygon2View`.

Following Family decision 2, no mechanical `Polygon3View` is admitted.

Consequently the entire public polygon-validation family remains 2D-only.

## Family decision 11 — Douglas-Peucker simplification

### Scope of this decision

This review covers the complete public `geo.simplification` surface:

~~~text
douglasPeuckerWorkspaceSize
trySimplifyDouglasPeuckerInto
~~~

That is two public declarations.

### Dimensional structure of Douglas-Peucker

The current simplifier operates on an ordered polyline.

For each current section it constructs the segment joining the section
endpoints and measures every intermediate point's Euclidean
point-to-segment distance.

The point with the greatest computed distance becomes the split point when
that distance exceeds the supplied tolerance.

None of those algorithmic concepts is intrinsically two-dimensional.

Following the geometry families already established by this audit:

~~~text
Polyline2View -> Point2 -> Segment2
Polyline3View -> Point3 -> Segment3
~~~

the same algorithmic structure applies naturally to three-dimensional
Euclidean polylines.

This shared-family conclusion concerns Euclidean geometry only.

It does not extend Douglas-Peucker automatically to geodesic coordinates,
spherical geometry, projected coordinate-system policy, or other non-Euclidean
distance models.

### Workspace size

The existing helper is:

~~~d
size_t douglasPeuckerWorkspaceSize(
    size_t pointCount
);
~~~

with the exact contract:

~~~text
max(pointCount - 2, 0)
~~~

The required workspace depends only on:

- the number of stored input points; and
- the iterative depth-first traversal structure.

It does not depend on coordinate dimension.

The public name therefore remains canonical:

~~~text
douglasPeuckerWorkspaceSize
~~~

However, this declaration differs from most shared operation families reviewed
earlier.

A hypothetical independent declaration in `geo3` would have exactly the same
public signature:

~~~d
size_t douglasPeuckerWorkspaceSize(
    size_t pointCount
);
~~~

There is no `Point2` / `Point3`, `Segment2` / `Segment3`, or view type in the
arguments with which D could distinguish the two declarations.

Consequently the declaration is conceptually cross-dimensional but requires
an explicit package-export decision before `geo` and `geo3` coexist.

Disposition:

~~~text
KEEP + COLLISION-REVIEW
~~~

The package-coexistence phase must decide where the single canonical public
workspace helper lives or how it is re-exported without ambiguous imports.

This audit does not introduce a common utility package merely to resolve that
question.

Nor does it create artificial names such as:

~~~text
douglasPeucker2WorkspaceSize
douglasPeucker3WorkspaceSize
~~~

because the workspace calculation itself is genuinely dimension-independent.

### Polyline simplification operation

Following Family decision 2, the canonical v2 2D signature becomes
structurally:

~~~d
bool trySimplifyDouglasPeuckerInto(T, R)(
    scope Polyline2View!T polyline,
    R tolerance,
    scope Point2!T[] destination,
    scope size_t[] workspace,
    out size_t written
);
~~~

A plausible `geo3-d` counterpart is:

~~~d
bool trySimplifyDouglasPeuckerInto(T, R)(
    scope Polyline3View!T polyline,
    R tolerance,
    scope Point3!T[] destination,
    scope size_t[] workspace,
    out size_t written
);
~~~

The operation name remains dimension-neutral.

Disposition:

~~~text
KEEP + SHARED-FAMILY
~~~

### Metric dependency

The simplifier delegates its geometric decision to point-to-segment distance.

Following Family decision 4, the canonical receiver order for that metric is:

~~~d
tryPointSegmentDistance(
    segment,
    point,
    result
);
~~~

The v2 simplification implementation should therefore use that canonical
segment-first form internally.

This is an implementation migration detail and does not alter the public
simplification signature.

The 3D family relies analogously on Euclidean:

~~~text
Point3 -> Segment3 distance
~~~

No new simplification-specific distance definition is introduced.

### Metric scalar

The tolerance type remains:

~~~text
MetricScalar!T
~~~

Following Family decision 4, that computation policy remains
dimension-neutral and subject to the later package-coexistence decision.

The simplification family does not introduce:

~~~text
SimplificationScalar
Simplification2Scalar
Simplification3Scalar
~~~

### Parameter order and UFCS

The existing parameter order remains canonical:

~~~text
polyline
tolerance
destination
workspace
written
~~~

The geometry is therefore the natural UFCS receiver:

~~~d
polyline.trySimplifyDouglasPeuckerInto(
    tolerance,
    destination,
    workspace,
    written
);
~~~

No reorder is justified.

The parameter names remain canonical.

### Workspace and destination contracts

The v2 migration preserves the existing caller-owned storage model.

For both dimensional families:

- destination capacity is at least the input point count;
- destination stores points of the same dimension and scalar as the input;
- workspace stores only `size_t` traversal state;
- workspace length is obtained from the same dimension-independent helper;
- input and destination must not overlap;
- no allocation is performed by the operation;
- `written` is zero on failure.

The dimensional migration must not introduce hidden allocation.

### Behavioural contract

The existing Douglas-Peucker behaviour remains unchanged:

- empty, singleton, and two-point inputs retain their established behaviour;
- first and last points are retained for inputs of length at least two;
- output consists only of selected input vertices;
- stored order is preserved;
- equality with tolerance permits removal;
- equal maximum distances select the first point in stored order;
- no topology-preservation guarantee is provided;
- non-finite tolerance is rejected;
- negative tolerance is rejected;
- non-finite input coordinates are rejected;
- required metric computations must produce finite representable results.

The same semantic structure is plausible for `Polyline3View`.

### Complexity

The established complexity contract remains:

~~~text
worst-case time          O(n^2)
caller workspace         O(n)
additional internal      O(1)
~~~

Coordinate dimension changes the constant cost of each metric operation but
does not change this API-level complexity model.

### v1 compatibility

The function names and argument order do not change.

For the simplifier, the canonical parameter-type spelling changes from:

~~~text
PolylineView -> Polyline2View
~~~

and v1 compatibility is supplied by the deprecated alias established in
Family decision 2.

No deprecated simplification forwarder is required.

`douglasPeuckerWorkspaceSize` itself does not change and requires no v1
compatibility declaration.

### No speculative simplification expansion

This migration does not add:

- ring simplification;
- polygon simplification;
- topology-preserving simplification;
- generic geometry simplification;
- geodesic Douglas-Peucker;
- alternative algorithms such as Visvalingam-Whyatt.

Those remain separate consumer-driven additions.

### Result of family decision 11

Accepted:

~~~text
douglasPeuckerWorkspaceSize
    KEEP + COLLISION-REVIEW
    same workspace formula applies across dimensions
    identical geo/geo3 signature requires package-export decision

trySimplifyDouglasPeuckerInto(Polyline2View, ...)
    KEEP + SHARED-FAMILY
    geo3-d:
        trySimplifyDouglasPeuckerInto(
            Polyline3View,
            tolerance,
            Point3[],
            size_t[],
            written
        )
    v1 PolylineView spelling preserved by deprecated alias
~~~

This completes declaration-by-declaration classification of the frozen v1
public surface.

## Package-coexistence decision

### Objective

The v2 naming grammar must permit a future consumer to use both libraries
together:

~~~d
import geo;
import geo3;
~~~

without forcing dimensional suffixes onto operations whose mathematical names
are naturally dimension-neutral.

A DMD 2.111.0 compile probe was therefore performed for three cases:

1. independent declarations in separate 2D and 3D package modules;
2. the same original declarations re-exported by both package modules;
3. declarations owned by the 2D package and re-exported through the 3D
   package.

### Probe result

The probe established:

~~~text
different typed function overloads     PASS

independent duplicate type             REJECTED
independent duplicate template         REJECTED
independent identical helper           REJECTED

common-origin dual re-export           PASS
geo-owned re-export through geo3       PASS
~~~

The failed independent cases were semantic name-resolution failures rather
than linker failures.

Therefore two independently declared symbols with the same root name cannot
be treated as one shared public contract merely because their definitions are
textually or semantically equivalent.

Conversely, both package modules may re-export the same original declaration
without creating ambiguity for the consumer.

### Operation rule

Dimension-specific operations may be independently implemented in `geo-d` and
`geo3-d` when their signatures distinguish the dimensional geometry.

For example:

~~~text
distance(Point2, Point2)
distance(Point3, Point3)

orientation(Point2, Point2, Point2)
orientation(Point3, Point3, Point3, Point3)

tryBounds(Segment2, Bounds2)
tryBounds(Segment3, Bounds3)
~~~

These remain independent library implementations under the same
dimension-neutral operation names.

### Shared-contract rule

A dimension-neutral non-overloadable public contract must not be independently
duplicated under the same package-root name.

When both `geo-d` and `geo3-d` actually need such a contract, they must expose
the same original declaration.

This applies to types, templates, enums, result structures, and helpers whose
public signatures do not contain a dimension-bearing type capable of
disambiguating independent overload sets.

Disposition vocabulary:

~~~text
KEEP + SHARED-ORIGIN-REQUIRED
~~~

means:

- the existing geo-d public name remains canonical;
- an eventual geo3-d counterpart must not independently redeclare the same
  root symbol;
- once the second real consumer exists, the declaration is moved or factored
  to one dimension-neutral origin;
- `geo` and `geo3` may then re-export that same original declaration;
- compatibility exports from the existing geo-d module paths must be retained
  where required.

### No geo3-d -> geo-d ownership dependency

The probe also proved that a 3D package can technically re-export declarations
owned by a 2D package.

That mechanism is not selected as the architecture.

`geo-d` remains the standalone 2D Euclidean geometry library.

A future `geo3-d` must not depend on `geo-d` merely to obtain
dimension-neutral contracts.

Such a dependency would assign shared Euclidean concepts to the 2D layer and
make the 3D library conceptually subordinate to it.

### Consumer-driven common origin

The coexistence review established that a shared declaration origin is
justified only when a second real sibling library requires the same public
contract with the same D declaration identity.

That condition is now met for the seven contracts identified below.

The integration therefore uses the narrowly scoped lower-level support
package `euclid-core-d`, as formalized by ADR-0020. Both dimensional sibling
libraries obtain the affected declarations from that common origin.

The extraction remains:

~~~text
consumer-driven
not speculative
required for common declaration identity
~~~

`euclid-core-d` is not a third consumer-facing geometry API and does not make
either dimensional sibling depend on the other.

### Compatibility of shared-origin extraction

The implemented common-origin extraction preserves the existing public
`geo-d` import surface.

For example, code using:

~~~d
import geo;

SegmentIntersectionKind kind;
RingValidationResult result;
~~~

continues to refer to the canonical shared declarations after extraction.

Supported module-level imports are preserved through aliases or re-exports
where source compatibility requires them.

The common declaration itself has one runtime identity; compatibility and
documentation facades must not create structurally identical but distinct
runtime replacement types.

### Shared-origin-required contracts

The current audit identifies seven root contracts that have an admitted
cross-dimensional consumer family and cannot safely be independently
root-exported by both libraries:

~~~text
isGeoScalar
MetricScalar
IntersectionScalar
SegmentIntersectionKind
RingValidationIssue
RingValidationResult
douglasPeuckerWorkspaceSize
~~~

Their enum members and public aggregate members inherit the same disposition.

These declarations therefore become:

~~~text
KEEP + SHARED-ORIGIN-REQUIRED
~~~

### AreaScalar remains geo-d-owned

`AreaScalar` is dimension-neutral as a numerical policy name, but this audit
did not admit a direct 3D counterpart for either:

~~~text
signedArea
polygonArea
~~~

~~~text
KEEP + 2D-ONLY
~~~

This does not prohibit a future 3D area API from eventually motivating a
shared scalar policy.

It means such an extraction is deferred until that API actually exists and
its numerical requirements are known.

### Root-package coexistence invariant

The integration probes exercise simultaneous root imports:

~~~d
import geo;
import geo3;
~~~

with representative calls from both dimensional operation families and with
common-origin declaration identity checks.

The probes establish the intended invariant:

~~~text
same mathematical operation
    -> same operation name where signatures disambiguate

same dimension-neutral contract
    -> same declaration identity

dimension-specific concept
    -> dimension-bearing type or 2D/3D-specific API as appropriate
~~~

This resolves the API-design question. Where coexistence evidence currently
exists only as temporary research or integration probes, the remaining freeze
work is to retain equivalent coverage as durable reproducible tests.

The previous `COLLISION-REVIEW` state is fully resolved.

No independently duplicated same-name neutral root contract is permitted.

No permanent `geo3-d -> geo-d` ownership dependency is introduced.

The shared `euclid-core-d` package is not speculative: it contains only
neutral contracts for which the second concrete sibling consumer established
a common-declaration-identity requirement.

Common-origin extraction has occurred only where that second concrete
consumer made it necessary.
